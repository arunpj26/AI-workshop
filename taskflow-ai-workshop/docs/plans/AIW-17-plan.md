## Requirements
- Confirmed requirements: Apply the branding and responsive dashboard; show current profile data without hardcoded personal details; compute summaries from task data; show the four specified board columns and available task details; include only supported navigation destinations; support search, priority/status filtering, create/add actions and clearing filters as agreed; preserve existing behavior and accessible focus/contrast.
- Assumptions: `OPEN` maps to the displayed `To Do` status; `IN_PROGRESS` and `COMPLETED` map directly. Show `On Hold` even when no tasks have that status. The existing task model is the source of truth: cards can currently display title, description, status and priority only. Because the app has only task data, one task-search control can search loaded task fields; project, date-range and assignee controls are omitted unless corresponding data/support is added. The board is read-only unless task-status mutation is explicitly approved. Use `/api/users/current` as the existing profile source for the baseline UI.
- Open questions: (1) `/api/users/current` currently returns server-configured values, not an authenticated session identity. Is that configuration-backed profile sufficient for this workshop, with account switching tested using different profile responses, or is an account-aware identity source expected? (2) Create Task and Add Task are required in the story, but the app has only `GET /api/tasks` and no persistence contract. Should implementation add a create endpoint, and if so what storage, required fields, validation, and initial status should it use? Until answered, do not implement a misleading local-only create action. (3) Should board status changes/drag-and-drop be included? There is no current mutation API, so this plan excludes them unless confirmed.
- Edge cases and risks: Missing name/role/image; failed or unsafe image URL; profile or task API failure; empty task list and zero-count summaries; no tasks in On Hold; no search matches; unsupported future task statuses must not silently disappear. The account-switching criterion cannot be guaranteed with the current configuration-backed profile endpoint. The create-action criterion cannot be met without an agreed API/data contract. Assignee, estimate, Jira key and activity/comment fields do not exist on `Task` and must not be fabricated.

## Backend plan  (owner: task-api-developer)
- Current contract: `GET /api/tasks` returns a JSON array of `Task(id,title,description,status,priority)`. `GET /api/users/current` returns `UserProfile(name,role,imageUrl)` from `taskflow.user.*` configuration; values are normalized and unsafe image schemes are rejected.
- Base scope: No backend changes for rendering the dashboard, calculating summaries, filtering the loaded task set, or displaying the current profile API response. Preserve both endpoint contracts.
- Decision-gated work: If task creation is approved, agree API payload, validation, initial status and persistence first; then update `TaskController`, `TaskService`, `Task` only if its shape must change, and `TaskControllerTest`. If an account-aware profile source is approved, identify the existing authentication integration first; do not add a new authentication system as an assumption.
- Existing relevant tests: `TaskControllerTest`; `UserControllerTest`; `UserControllerConfiguredUserTest`; `UserControllerMissingProfileTest`; `UserProfileServiceTest`. Add only focused tests for any approved backend contract changes.
